# Polish with the running app open

**Use when:** the change has a surface a person experiences — UI, copy, output formatting — and the checks are already green.

**Do:**
- Treat "all checks pass and the review agents are silent" as the start of your review, not the end of it.
- Check out the branch, start the dev server, and put the running thing beside the agent; script that setup so the friction of looking at it is near zero.
- Use the feature yourself, then say what feels wrong in plain language — animation direction, density, spacing, copy — and look again after the reload.
- Keep going until it stops feeling wrong, then fold the lessons back into the instructions.
- Make polish a named stage after review, not an optional mood.

**Why:** passing review and being good are different states. A plan can ask for a magazine feel; only a person looking at the page can say when the density is right, and that judgement is about qualities the model has no access to.

**Don't / when not:** don't try to specify polish up front — this feedback is generated by looking, not by writing a spec.

**Evidence:**
- [every-2026-07-13-polish-agent-built] a PR passed every automated check with nothing left for the review agents to flag, yet the email card animated in from the top of the screen instead of opening from where he clicked; the fix came from a scripted command that checks out the branch, starts the dev server, and opens the running app next to the agent while he says what feels off.
- [every-2026-05-29-compound-engineering-upgrade] the loop gains an explicit polish stage after review, because a build can pass review and still be bad.
