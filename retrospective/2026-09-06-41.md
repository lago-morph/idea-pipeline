## Part 1 — what happened

### Phase 1 — transcribing a handwritten PDF

The owner attached a tablet export of handwritten architecture notes and asked for a verbatim markdown transcription with spelling and formatting normalized, the boxed "DoD" glyphs used as markers for a definition-of-done table at the end, and the glyphs themselves omitted. The built-in PDF reader failed for lack of `pdftoppm`. Installing `pymupdf` showed one page, 514 by 4189 points, with no text layer, no images, and 2060 vector drawings. Rendering it in ten overlapping strips at 200 dpi made it legible; two regions were re-rendered at 250 dpi to settle a suspicious gap and a strip boundary. The transcription landed as PR #40 with a four-row DoD table, and the reply flagged two readings for the owner to check. The PR merged within minutes.

### Phase 2 — discussion, and the first capture

The owner then opened a discussion: structure all the decisions needed to go from an idea to a running system, because fuzzy architecture fails when agents must produce specifications from it. Three turns of discussion produced the ideas of decision slots with explicit status, binding time, a profile that drives an applicability matrix, artifacts as the unit with five kinds of guidance, and subject-primary organization with concern as the audit view. The owner asked for the process suggestions and an objectives statement captured as drafts. Because PR #40 had merged, the branch was restarted from main before `objectives.md` and `ideas.md` were written and PR #41 opened.

### Phase 3 — orienting on agent-method and writing the nuggets

The owner pointed at the agent-method repository and asked for its objectives and status to be understood, then for the discussion to be preserved so ideas could be pulled into agent-method over time. The repository was cloned to `/tmp` per the owner's preference and read by two Explore subagents, one for `method/` and `ai/`, one for `workbench/`, with four small convention files read directly. The reports showed agent-method already had most of the discussed machinery under its own names: the ambiguity list, the regeneration test, the guide / decisions / standard pattern, and six foreseen guides. Fourteen one-screen idea files and an index were written, each idea with a free-text trigger.

### Phase 4 — the spine

The owner pushed back: nuggets pulled one at a time into free-form notes reproduce the collapse agent-method's archived attempts suffered, and the structure that ties artifacts, concerns, and subjects together for a whole system was missing. A six-structure spine was sketched in conversation, with modes, verification, and a harvest loop riding on it. The owner said "love it" and asked for everything written up, with artifacts, maturity criteria, a system profile, an inventory, and a plan. The overview and decision-record documents were written directly, three general-purpose subagents drafted the other eight spine documents in parallel from that overview, and the plan, inventory, decisions log, objectives revision, and index were written while they ran. A consistency pass found one contradiction, end-user management at two maturity levels, and one stale sentence. All of it was committed in three checkpoints.

### Phase 5 — the interface, twice

The owner found the nugget triggers confusing and ambiguous. Diagnosis: the free-text triggers mixed four kinds of condition, some fired continuously, some joined conditions with "or", and the plan used different words for the same events. The fix replaced triggers with one relationship kind per idea and one event from a fixed list, using codes such as E1 and G. The owner rejected the codes as confusing for things he had to review or follow. A second pass wrote out every event and every maturity level by name across twenty files, and recorded the no-codes rule as owner-stated in the decisions log. PR #41 merged shortly after.

### Phase 6 — stewardship

Hourly check-ins were scheduled on each open PR and re-armed silently when nothing changed. The PR description was refreshed after each substantive push. Both merges arrived as events and the pending check-in was deleted each time. The `human-scoped-deliverables` skill, which lives in this repository and whose vocabulary rule would have prevented the code rewrite, was available throughout and never loaded. That is the session's clearest miss.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory at `./2026-09-06-41/AGENTS-MD-<hash>-<kebab-name>.md`. The per-rule file contains exactly two sections: `# agent instruction` (the verbatim rule text the CI/CD assembler concatenates into `AGENTS.md`) and `# justification` (the persuasion text the assembler strips out).

This Part 3 mirrors that content inline so the retrospective reviewer has every proposed rule and its justification in one place at review-decision time.

### Suggestion 1: No invented codes for anything the owner reviews or follows — `AGENTS-MD-ba891cab20`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-ba891cab20-no-invented-codes-for-anything-the-owner-reviews-or-follows.md](./2026-09-06-41/AGENTS-MD-ba891cab20-no-invented-codes-for-anything-the-owner-reviews-or-follows.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **No invented codes for anything the owner reviews or follows.** Write events, levels, phases, and categories out by name everywhere they appear: in tables, in front matter, and in prose. Do not coin short codes such as E1, G, or M2 for things a human must review, compare, or act on, even when a code would make a table narrower. If an ordering matters, let the table order or a descriptive name carry it.
>
> *Grounded in: the event-code and maturity-code rewrite across twenty files in PR #41.*

**Justification** (verbatim from the per-rule file's `# justification` section):

In PR #41 the interface between the ideas directory and agent-method was first written with event codes (E1 through E7, G, M) and the maturity ladder with level codes (M0 through M5). The owner's response was that abbreviations like that are very confusing and that codes should not be made up for things he needs to review or follow. Undoing it took a full pass over the README, the plan, the decisions log, fourteen nugget front matters, and five spine documents, plus a PR description rewrite. The codes had saved a few characters per table cell and nothing else. Writing names costs a wider column. The asymmetry is a twenty-file rewrite against a wider column, and the rule is one sentence to remember.

### Suggestion 2: Load human-scoped-deliverables before writing anything the owner will read — `AGENTS-MD-227e79e61f`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-227e79e61f-load-human-scoped-deliverables-before-writing-anything-the-owner-will-read.md](./2026-09-06-41/AGENTS-MD-227e79e61f-load-human-scoped-deliverables-before-writing-anything-the-owner-will-read.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Load human-scoped-deliverables before writing anything the owner will read.** Before drafting a summary, plan, index, or design document whose reader is Jonathan rather than another agent, invoke the `human-scoped-deliverables` skill and follow its vocabulary discipline. Its rule against invented jargon covers coined codes, coined labels, and any term not already in the corpus.
>
> *Grounded in: the skill existed in this repository and was not loaded before the architecture documents were written.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The `human-scoped-deliverables` skill sits in this repository's `.claude/skills/` and its description names exactly the failure that happened: invented jargon over corpus terms, cognitive load as a real resource. It was listed as available in every turn of the session and never invoked, because the documents were framed as design drafts rather than as summaries or primers. The result was the event-code rewrite described in the previous rule, which the skill's vocabulary rule would have prevented before the first draft. The cost of loading the skill is one tool call at the start of a writing task. The cost of not loading it was a twenty-file rewrite and a round-trip with the owner.

### Suggestion 3: Specify when something applies as a closed list of named conditions — `AGENTS-MD-8c9af3aca7`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-8c9af3aca7-specify-when-something-applies-as-a-closed-list-of-named-conditions.md](./2026-09-06-41/AGENTS-MD-8c9af3aca7-specify-when-something-applies-as-a-closed-list-of-named-conditions.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Specify when something applies as a closed list of named conditions.** When a document says when an item is needed, pulled in, or triggered, define a short fixed list of named conditions once, give every item exactly one condition and one relationship to it, and do not join conditions with "or". Do not mix work items, thresholds, symptoms, and external events in the same free-text field.
>
> *Grounded in: the fourteen nugget triggers the owner called confusing and ambiguous.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The first version of the fourteen nugget files each carried a free-text `trigger:` line. Some named a work item already on agent-method's plan, some named a threshold such as more than about five guides, some named a symptom of a run, and some named an external event that might never happen. Several joined two conditions with "or". The plan's sync table described the same events in different words. The owner's verdict was that the conditions and trigger points were confusing and ambiguous. The fix was a nine-row table of named events, three relationship kinds, and one of each per nugget, and it took one pass. Defining the closed list first would have cost the same pass and avoided the round-trip. Free-text conditions read fine one at a time and fail as a set.

### Suggestion 4: Mark every recorded conclusion as owner-stated or proposed — `AGENTS-MD-5ef6119584`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-5ef6119584-mark-every-recorded-conclusion-as-owner-stated-or-proposed.md](./2026-09-06-41/AGENTS-MD-5ef6119584-mark-every-recorded-conclusion-as-owner-stated-or-proposed.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Mark every recorded conclusion as owner-stated or proposed.** When capturing a discussion into files, keep a decisions log in which each conclusion is labeled with who settled it: the owner in conversation, or the agent as a proposal awaiting the owner's word. Never present an agent's inference as settled. A merge is not ratification.
>
> *Grounded in: `architecture-ideas/decisions-log.md`, which carried 37 labeled conclusions from one session.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The session produced dozens of conclusions across six hours of discussion, and roughly a third of them were the owner's and two thirds were proposals. Without a label, a future session would read the proposals as settled and build on them, which is the exact failure agent-method's own lessons record under "label AI-inferred intent as unratified". The decisions log made the split explicit: each row says owner, proposed, or owner-agreed, and the open questions are listed separately. It cost one table. It is also what let the objectives document say "inferred" honestly and what let the subagents' judgment calls be logged as proposals rather than facts. The marginal cost is one column; the alternative is a document set whose provenance cannot be recovered.

### Suggestion 5: Write the authoritative overview before fanning out drafts — `AGENTS-MD-c035b82fe9`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-c035b82fe9-write-the-authoritative-overview-before-fanning-out-drafts.md](./2026-09-06-41/AGENTS-MD-c035b82fe9-write-the-authoritative-overview-before-fanning-out-drafts.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Write the authoritative overview before fanning out drafts.** When splitting a document set across parallel subagents, write the overview that fixes vocabulary and structure first, commit it, and make every subagent read it before drafting. Order dependent drafts so a subagent never has to assume a sibling document that does not exist yet. Ask each subagent to end with a five-line list of the judgment calls it made.
>
> *Grounded in: the registry draft that had to be realigned after the maturity ladder landed mid-flight.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Three general-purpose subagents drafted eight spine documents in parallel. All three read `spine/overview.md` and `spine/decision-record.md` first, and the drafts came back using one vocabulary, which is why the consistency pass found only one contradiction across nine files. The one problem was a dependency: the registry's "first required at" column needed the maturity ladder, which another subagent was writing at the same time. The registry subagent used an assumed ladder, then re-read the real one when it appeared and moved eleven values. That worked, but only because the subagent noticed. Sequencing the ladder before the registry would have cost a few minutes of wall clock. The five-line judgment-call summary from each subagent was what made review cheap: every deviation was named, and four of them went straight into the decisions log.

### Suggestion 6: Stage files by name while background subagents are writing — `AGENTS-MD-371f222957`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-371f222957-stage-files-by-name-while-background-subagents-are-writing.md](./2026-09-06-41/AGENTS-MD-371f222957-stage-files-by-name-while-background-subagents-are-writing.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Stage files by name while background subagents are writing.** Do not run `git add` on a directory that a background subagent is writing into. Stage the specific files you own. A directory-level add captures a sibling's half-written file in your commit.
>
> *Grounded in: commit a89a9b5, which captured the artifact type registry mid-draft.*

**Justification** (verbatim from the per-rule file's `# justification` section):

While three subagents were writing into `architecture-ideas/spine/`, a checkpoint commit ran `git add architecture-ideas/spine` to save six finished drafts. It also swept up the registry file that one subagent was still writing, so that commit carries a half-finished registry and the next commit carries its correction. Nothing broke, but the history now misrepresents when the registry was done, and the subagent had to report the capture in its summary. Naming the six files instead of the directory would have cost one longer command line. Checkpoint commits during fan-out are worth making; they just have to be scoped to what is actually finished.

### Suggestion 7: Use absolute paths in parallel Bash calls — `AGENTS-MD-d8b57f9989`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-d8b57f9989-use-absolute-paths-in-parallel-bash-calls.md](./2026-09-06-41/AGENTS-MD-d8b57f9989-use-absolute-paths-in-parallel-bash-calls.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Use absolute paths in parallel Bash calls.** The shell's working directory persists between calls, and a `cd` in one call changes where a parallel call's relative paths resolve. Every file path in a Bash call that may run alongside another must be absolute.
>
> *Grounded in: idea files written with relative paths that landed correctly only because a parallel `cd` had already run.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Two Bash calls ran in parallel to write fourteen nugget files. The first began with `cd .../architecture-ideas/ideas`. The second used `mkdir -p` with an absolute path and then wrote files with bare relative names. The files landed in the right place only because the first call's `cd` had already changed the persistent working directory. Had the calls interleaved differently, eight files would have been written to the repository root, and the `ls` that followed would have caught it only by luck. The environment notes confirm the working directory persists and that `cd` in a compound command is discouraged. Absolute paths cost nothing and remove the race.

### Suggestion 8: Read review batches in chunks under 25 KB — `AGENTS-MD-e1813b691d`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-e1813b691d-read-review-batches-in-chunks-under-25-kb.md](./2026-09-06-41/AGENTS-MD-e1813b691d-read-review-batches-in-chunks-under-25-kb.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Read review batches in chunks under 25 KB.** When reading several files back for review in one call, keep the total under about 25 KB. Larger outputs are written to a file instead of returned, and reading them again costs a second pass.
>
> *Grounded in: a 36 KB four-file read that was persisted to disk and re-read in halves.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Reviewing four subagent drafts with one `cat` produced 36 KB, which the harness persisted to a file and returned as a 2 KB preview. The four files then had to be read again in two calls. The threshold is not documented, but 36 KB was over it and two calls of about 18 KB each were under it. The cost of the miss was one wasted call and the context of the preview. The rule costs nothing: split the read before running it.

### Suggestion 9: Orient in a foreign repository through Explore subagents with cited reports — `AGENTS-MD-5c8cfe31d2`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-5c8cfe31d2-orient-in-a-foreign-repository-through-explore-subagents-with-cited-reports.md](./2026-09-06-41/AGENTS-MD-5c8cfe31d2-orient-in-a-foreign-repository-through-explore-subagents-with-cited-reports.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Orient in a foreign repository through Explore subagents with cited reports.** To understand another repository's objectives and status, clone it to `/tmp`, split it into two or three bounded reading assignments, and have Explore subagents return reports under 1500 words with a file path for every claim, a vocabulary list, and no critique. Read yourself only the few files whose exact shape you must mirror.
>
> *Grounded in: the two agent-method reports that fed the spine without loading 500 KB of notes into the main context.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Agent-method's non-archive content is about 500 KB across 109 files. Two Explore subagents read it in full and returned reports of about 1500 words each, with file paths on every claim and a twenty-term vocabulary list. Those two reports, plus four small files read directly because their exact conventions had to be mirrored, were enough to design a structure that slots into agent-method's own patterns. The main context spent perhaps 8 KB on the repository instead of 500 KB. The brief's constraints did the work: a fixed report outline, a word cap, "do not critique", "quote with file paths", and a vocabulary section. The vocabulary section in particular is what let every later document use agent-method's words rather than coined ones.

### Suggestion 10: Run a cross-file consistency check before pushing a document set — `AGENTS-MD-39c427b451`

- **Per-rule file**: [./2026-09-06-41/AGENTS-MD-39c427b451-run-a-cross-file-consistency-check-before-pushing-a-document-set.md](./2026-09-06-41/AGENTS-MD-39c427b451-run-a-cross-file-consistency-check-before-pushing-a-document-set.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Run a cross-file consistency check before pushing a document set.** After multi-file edits, check that every file another file references exists, that no em or en dashes crept in, that headings stay within the agreed depth, and that any fact stated in two files agrees. Fix contradictions at the source and record them in the decisions log.
>
> *Grounded in: the end-user management criterion that the maturity ladder placed at two different levels.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The maturity ladder's entry criteria put end-user management at the Enterprise level while its own criteria matrix put it at the Operated level. The registry subagent noticed the disagreement and flagged it in a table cell rather than resolving it. A single grep-and-read pass over the finished set found it, along with a stale sentence in `ideas.md` that still said the data model came first. The pass took one command: a dash check, a heading-depth check, an existence check on every `spine/*.md` path referenced from the index files, and targeted greps on the two facts the subagent summaries had flagged. Without it, the contradiction would have shipped in the owner's review copy. The `post-edit-reread-pass` skill describes the principle; this rule names the four concrete checks that caught real errors.
