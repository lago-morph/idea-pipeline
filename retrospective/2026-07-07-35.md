## Part 1 — what happened

The session began as a review conversation, not an implementation task: the owner had comments on the four `spec-completeness/` documents (`README.md`, `artifact-model.md`, `process.md`, `hardening/`) produced by earlier sessions, and delivered them across several feedback rounds with an explicit instruction to hold all changes until the feedback converged. It ended with the entire framework reshaped around a new central abstraction (use cases), recorded as five ADRs and merged as three PRs.

### Phase 1 — analysis-only review rounds

The owner's opening comments — use cases are missing; can they be inferred from a "golden" spec; where would documentation live — were answered by reading the four documents in full and reasoning about them, with no edits. Successive turns stress-tested the model against a documentation mandate (Diátaxis), interrogated the difference between the proposed artifacts and traditional use cases, and objected to two structural choices (the freedom register, and the assumption that all implementations are one-shot-and-discard). The discipline of not editing during this phase mattered: the design moved a long way before any file changed.

### Phase 2 — a sharp communication correction

When the accumulated feedback was turned into a set of pre-implementation decision questions, the owner pushed back hard on the *language*: coined shorthand ("amendment", "staged") and decision-topics-named-as-documents were unreadable. The questions were re-asked in plain language with named files, plain alternatives, and rewind paths. This repo already ships a `human-scoped-deliverables` skill encoding exactly that; the miss was not applying it. The correction is captured as an agents-file rule below.

### Phase 3 — importing skills and recording decisions (PR #33)

At the owner's request, two skills (`adr`, `human-scoped-deliverables`) were copied from `lago-morph/software-factory` via a sparse clone. The five converged decisions were then recorded as ADRs 0001–0005 using the newly-imported `adr` skill, `docs/adr/` was bootstrapped, and the link checker passed. Crucially, the ADRs were adopted *before* any of the four framework documents were touched — they became the source of truth the reshape was checked against.

### Phase 4 — the reshape in two review rounds (PRs #34, #35)

The owner chose a staged review: round one (PR #34) rewrote the two shape-defining documents (`artifact-model.md`, `process.md`) around use case documents, maturity levels L0–L3, consistency rules C1–C10 (replacing the old T1–T7), and a whole-life process with delivery and standing-maintenance stages; round two (PR #35) realigned the checklist and the 55 executable checks to match. During the in-between window the two lagging documents carried explicit alignment notes naming what controlled on conflict. Each round ran a re-read pass plus targeted greps before commit; round one's re-read caught five cross-section drift bugs (a question-class name colliding with a status, a mis-formatted example ID, an omitted rule in a lint list, two missing metric definitions, an undefined term), and round two verified the check suite's bidirectional totality (55 defined = 55 referenced) and swept out retired vocabulary.

### Phase 5 — an owner question that found a real gap

Mid-review the owner asked why the architecture sketch was "advisory" and why the process and artifact documents seemed disconnected. Answering the second question required a cross-enumeration join that the per-document reviews had not — and it exposed that the "Shared Examples" section had been defined with no corresponding file in the shape table, workspace tree, or production map. The orphan was fixed (adding `shared/examples.md` to four enumerations) in the round-one review-fix commit. This is the origin of the set-membership agents-file rule below.

### Phase 6 — check-ins and infrastructure friction

Each PR was subscribed for activity and an hourly self-check-in was armed via `send_later`. MCP servers (github, Claude_Code_Remote, Context7) flapped repeatedly through the session; the final check-in re-arm failed three times on permission-stream / server-disconnect errors. Rather than loop-hammer the flapping tool or go silently un-armed, the situation was surfaced honestly to the owner. (Both failure modes were already captured as rules in the prior retro `2026-07-05-31`; see Part 3.)

## Part 3 — agents-file suggestions

Four new rules, each with a per-rule file in the sibling directory carrying `# agent instruction` (concatenated into `AGENTS.md` by the CI/CD assembler) and `# justification` (stripped by it). Both are mirrored inline below.

**Recurrences worth noting (no new files — already captured in `2026-07-05-31`):** three lessons recurred this session and their prior IDs stand as confirming evidence rather than duplicates — the retired-vocabulary sweep (`AGENTS-MD-623541129c`, re-exercised in round two), branch-reset-invalidates-your-reads (`AGENTS-MD-da46b274ee`, re-hit when a Write failed on a restored `artifact-model.md`), and permission-stream failures are unanswered prompts (`AGENTS-MD-80bad1f7fd`, re-hit on the `send_later` re-arm). ### Suggestion 1: Pin owner decisions as ADRs before a multi-file reshape — `AGENTS-MD-7785992d7e`

- **Per-rule file**: [./2026-07-07-35/AGENTS-MD-7785992d7e-adr-first-reshape.md](./2026-07-07-35/AGENTS-MD-7785992d7e-adr-first-reshape.md)

**Proposed agent instruction:**

> **Pin owner decisions as ADRs before a multi-file reshape.** When a review or design conversation produces binding decisions that will drive edits across more than one document, record each decision as an ADR (via the `adr` skill) *before* editing the documents. Treat the ADRs as the source of truth the edits are checked against, not as after-the-fact documentation.
>
> *Grounded in: recording ADRs 0001–0005 before rewriting the four spec-completeness documents.*

**Justification:**

This session's reshape touched four interdependent documents plus 55 executable checks, against five owner decisions accumulated over many feedback rounds. Recording them as ADRs *first* gave every subsequent edit a stable, citable target and let the owner approve the decisions once, at the ADR stage, rather than re-litigating them inside four separate diffs. The alternative — decisions living only in chat that truncates — leaves no way for a later session (or the owner) to answer "why does this section say this?" without replaying the review. Marginal cost: five short files and one link-check run, front-loaded. The payoff compounds across every document the decisions touch. For single-file changes, skip it; the rule targets the multi-file case where inter-document drift is the real risk.

### Suggestion 2: Mark not-yet-realigned documents with an explicit precedence note — `AGENTS-MD-597ac31a9b`

- **Per-rule file**: [./2026-07-07-35/AGENTS-MD-597ac31a9b-alignment-note-partial-reshape.md](./2026-07-07-35/AGENTS-MD-597ac31a9b-alignment-note-partial-reshape.md)

**Proposed agent instruction:**

> **Mark not-yet-realigned documents with an explicit precedence note.** When a reshape touches a family of interdependent documents in stages, every document that is not yet updated must carry a visible note stating that it is stale relative to the change and naming which document (or ADR) controls on conflict. Remove the note only when that document is realigned.
>
> *Grounded in: the round-one/round-two split where the README checklist and hardening checks lagged the two shape documents.*

**Justification:**

The reshape ran in two review rounds — separate merged PRs, days apart, separated by other work — during which the four documents were mutually inconsistent by design: the shape documents described use cases while the checklist still described the retired model. Without a marker, a reader landing on the stale checklist during that window takes it as current and builds on a superseded model. The fix was a one-paragraph alignment note stating which documents were already realigned and that "this document and the ADRs control on conflict." Cost: one paragraph per document, deleted when it is brought current. Cost of omitting it: a reader silently trusting stale normative text — the exact failure the reshape existed to prevent — with no signal the inconsistency is intentional and temporary.

### Suggestion 3: Name the concrete thing when surfacing a decision to a human — `AGENTS-MD-02b133a743`

- **Per-rule file**: [./2026-07-07-35/AGENTS-MD-02b133a743-name-the-concrete-thing.md](./2026-07-07-35/AGENTS-MD-02b133a743-name-the-concrete-thing.md)

**Proposed agent instruction:**

> **Name the concrete thing when surfacing a decision to a human.** When presenting a choice for the human owner to decide, never refer to work products or steps by a shorthand you coined mid-session ("the amendment", "staged", "the realignment"). Lead with the concrete thing — the actual file, the actual alternatives in plain words, the trade-off, and the cost of choosing wrong. The reader cannot see your internal labels.
>
> *Grounded in: the owner's correction that "amendment" and "staged" were invented shorthand they could not read.*

**Justification:**

Presenting the pre-implementation decisions with coined shorthand ("one amendment vs. staged") drew a blunt correction: "what fucking do you mean about 'amendment'... you are making up your own language... 'staged' is not an alternative. It is a buzzword you made up." The whole batch had to be re-asked in plain language, costing a full round-trip and eroding trust. This repo already ships `human-scoped-deliverables` saying exactly this; the failure was not following it. The marginal cost of the rule is *negative* — plain naming is less work to write and less work to read. Coined shorthand has no upside when the audience is a human who was not in your head when you coined it.

### Suggestion 4: Every member of a defined set needs a home in every enumeration of it — `AGENTS-MD-6e5983d357`

- **Per-rule file**: [./2026-07-07-35/AGENTS-MD-6e5983d357-set-member-every-enumeration.md](./2026-07-07-35/AGENTS-MD-6e5983d357-set-member-every-enumeration.md)

**Proposed agent instruction:**

> **Every member of a defined set needs a home in every enumeration of it.** When a document defines a set of artifacts, sections, or components, verify that each member appears in *every* place the set is enumerated — the overview table, the directory layout, the production map, the per-stage outputs. A member defined in one enumeration but missing from another is a latent defect, even when every individual list looks internally complete.
>
> *Grounded in: the Shared Examples section that had no file in any workspace layout until the owner questioned the artifact/process disconnect.*

**Justification:**

The rewritten `artifact-model.md` defined a "Shared Examples" section — contents, boundary, consistency link — but it had no file in the shape table, the workspace tree, the production map, or any stage's outputs. Every enumeration looked internally complete, so no single-document review caught it; it surfaced only when the owner's broad question forced a cross-enumeration join. The fix was trivial; the risk was shipping a section a builder is told exists but can never locate. The check is a cheap deterministic sweep — extract the member set from its defining enumeration, confirm each member appears in every other enumeration. Sets enumerated in multiple places are exactly where this drift hides, because each list is locally consistent and only the cross-product reveals the gap.
