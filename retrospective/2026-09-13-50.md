## Part 1 — what happened

### Phase 1 — diagnosis, before any repair

The session opened as a question, not a task: two complaints about the `agent-patterns` wiki, and an ask for whether re-ingesting sources and regenerating an artifact would fix them, or whether something more direct was needed. The diagnosis changed the shape of the work. The "many sources based only on abstracts" turned out to be exactly three of forty-nine, all arXiv, all with reachable full texts — and separately six paywall-truncated newsletter notes that no amount of re-ingesting can fix, because the corpus's own charter puts paid content out of scope. The truncated router was worse than reported: 30 of 36 rows cut mid-sentence, and one empty.

The load-bearing finding was that there was no generator to fix. The artifact had been produced by a one-off regex, and its entire specification was a parenthetical. So the answer to the user's framing question was "address it directly, at the contract level" — and the same pass established that the build had stopped at its own Checkpoint B, with the dogfood phase never run.

### Phase 2 — re-ingest, and the discovery that the notes were wrong

Three readers took one paper each. The instruction that mattered was to report corrections, not summaries. All three came back with the source note materially misstating its paper. One note had inverted a paper's central claim about when controls can be derived. Another had laundered four unrepeated single sessions with no statistics into a confident effect size, and had reported it as a cost figure when the paper measured tokens and wall-clock with correctness unchanged at 5/5. A third had generalised eleven of thirteen participants into all of them. The re-ingest was not a cosmetic pass; it was a correction pass.

### Phase 3 — contract, then artifact

The router was fixed in the order that mattered: the contract into SPEC first, defining what a row's trigger must contain and requiring that it be authored rather than extracted; a generation-check section requiring generated files be read back; then all 36 triggers rewritten by hand and verified mechanically. Every later change in the session re-ran that check, and it caught a label mismatch the moment a page's status changed.

### Phase 4 — the owner's positions arrive, and pages start dying

The user rejected the `unreviewed-code` anti-pattern outright on his own experience. That decision was not made in one step: three options were put to him, he chose deprecation, and later extended the same disposition to `review-agent-diffs`. Between those two decisions the corpus gained its first first-hand source — the user's own failed platform project and its forensic analysis — which supplied both the hardest evidence in the corpus and, awkwardly, evidence against one of the corpus's existing claims.

### Phase 5 — the transcript, excluded and then restored

Mid-session the user interrupted to say one file of the source was incomplete and must not be used. The attempt to redirect the reader handling it failed — the interrupt had already stopped all four background agents — so three were relaunched with the exclusion written into their briefs. Later the file was completed and a fresh reader folded it in. It corrected two figures in the just-written note, and it corrected a framing error of this session's own: the earlier pass had filed the source as counter-evidence against capturing lessons, when the source showed capture was the load-bearing part and only rule-emission had failed. That error had already been committed.

### Phase 6 — the owner's model, written down

The user then supplied the reasoning the corpus had been missing: capture is vital and is the only practical way to improve; what fails is only ever the remedy channel; harness hooks beat prose because the agent and harness can ignore prose; retrospectives are historical data mined in bulk, not to-do lists. That rewrote one page, created two anti-patterns at his direction, and produced one placeholder for a direction he has stated but not yet demonstrated. The final exchange added the honest qualifier that deterministic controls are not free — they are the better trade — and paired the two pages as opposite faces of one problem.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory at `./2026-09-13-50/AGENTS-MD-<hash>-<kebab-name>.md` — that file carries the rule under `# agent instruction` (concatenated into `AGENTS.md` by the CI/CD assembler) and the persuasion under `# justification` (stripped by the assembler). This Part 3 mirrors both inline so the reviewer has every proposed rule and its justification in one place at decision time.

### Suggestion 1: Two evidence lines from one source is not corroboration — `AGENTS-MD-76b21f2973`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-76b21f2973-two-evidence-lines-from-one-source-is-not-corroboration.md](./2026-09-13-50/AGENTS-MD-76b21f2973-two-evidence-lines-from-one-source-is-not-corroboration.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Two evidence lines from one source is not corroboration.** "When a promotion or confidence threshold counts evidence, count independent sources, not lines. A second line drawn from the same source is more detail on one finding; never write one to clear a threshold, and never promote on one."
>
> *Grounded in: two pages in this session deliberately given a single evidence line to avoid tripping a "≥ 2 evidence lines" promotion rule.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The threshold in this corpus was written as "promote candidates with ≥ 2 evidence lines". Twice in one session a page was deliberately given one evidence line, despite its source supporting two distinct observations, purely to avoid an automatic promotion on a single finding. Meanwhile three existing candidate pages were found carrying two and three lines each from a single source, correctly unpromoted — an earlier session had silently applied a stricter rule than the one written down. A rule that every reader quietly reinterprets is not doing any work, and the reinterpretations diverged in both directions. The marginal cost of the fix is one word in the rule text. The cost of leaving it is that the injectable artifact an agent loads gets populated by whoever split one finding into two sentences.

### Suggestion 2: Own project and own experience are one source — `AGENTS-MD-026b872bee`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-026b872bee-own-project-and-own-experience-are-one-source.md](./2026-09-13-50/AGENTS-MD-026b872bee-own-project-and-own-experience-are-one-source.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Own project and own experience are one source.** "When material from a practitioner's own project and that practitioner's own stated experience both support a claim, they corroborate each other not at all. Count them as one source for any threshold, and say so where the claim is recorded."
>
> *Grounded in: two anti-patterns held at candidate because their two evidence lines were the owner's project and the owner's own statement.*

**Justification** (verbatim from the per-rule file's `# justification` section):

This session ingested the corpus owner's own project as a source, and separately recorded his stated position from conversation as own experience. Counted as documents, two new anti-patterns each had two evidence lines and cleared the promotion bar. Counted as perspectives, both lines were one person, and promoting on them would have put one practitioner's word into the injectable checklist wearing the costume of corroboration. Holding them at candidate cost nothing — the pages exist, they are findable, and the status accurately says what is known. The asymmetry is stark: the check is a single question asked once per promotion, and the failure mode is a corpus that silently launders self-agreement into consensus.

### Suggestion 3: Ask a subagent what you got wrong, not whether you are right — `AGENTS-MD-82e85ad05c`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-82e85ad05c-ask-a-subagent-what-you-got-wrong-not-whether-you-are-right.md](./2026-09-13-50/AGENTS-MD-82e85ad05c-ask-a-subagent-what-you-got-wrong-not-whether-you-are-right.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Ask a subagent what you got wrong, not whether you are right.** "Every research or review brief must ask explicitly for contradictions, for what the existing record gets wrong, and for anything that cuts against the position you just stated — and must say not to soften it in either direction. A brief that asks for confirmation gets confirmation."
>
> *Grounded in: the three highest-value findings of this session all arrived under a 'what does this contradict?' heading.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Every brief in this session carried a section asking what the source contradicted and what the existing note had got wrong. That section returned: a source note whose central claim was inverted relative to the paper, a headline statistic that turned out to be four unrepeated sessions with no statistics, and a framing error of the orchestrator's own that had already been committed. None of those would have surfaced under "summarise this source". One brief went further and named the owner's stated position with the instruction to say plainly if the source cut against it — and the reader returned exactly that, which became a correction the owner acted on. The marginal cost is three sentences per brief. The cost of omitting them is a research pass that reliably confirms whatever the orchestrator already believed.

### Suggestion 4: Tell a subagent it may correct the brief — `AGENTS-MD-c573a9dfd8`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-c573a9dfd8-tell-a-subagent-it-may-correct-the-brief.md](./2026-09-13-50/AGENTS-MD-c573a9dfd8-tell-a-subagent-it-may-correct-the-brief.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Tell a subagent it may correct the brief.** "When a brief asserts something about a source — its fidelity, its scope, what it contains — instruct the reader to verify that assertion against the source and to correct you if it is wrong. Read its correction before using its findings."
>
> *Grounded in: a brief that told a reader to treat part of its file as low-fidelity; the reader found a note superseding that caveat and said so.*

**Justification** (verbatim from the per-rule file's `# justification` section):

A brief in this session instructed a reader to mark everything before a certain point in its file as summary-fidelity rather than verbatim, because an earlier version of the file had carried that caveat. The reader read the file, found a section stating the document had since been rebuilt from a full log by a deterministic script with no compaction, and opened its report by correcting the brief. That correction materially upgraded the source: the sections carrying the owner's own statements were verbatim, not summary. Had the reader followed the brief obediently, every finding from those sections would have been discounted for no reason. One clause in the brief buys a reader who checks the orchestrator's assumptions instead of inheriting them.

### Suggestion 5: Quote the exact text you want judged — `AGENTS-MD-518ca3d960`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-518ca3d960-quote-the-exact-text-you-want-judged.md](./2026-09-13-50/AGENTS-MD-518ca3d960-quote-the-exact-text-you-want-judged.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Quote the exact text you want judged.** "When asking a subagent to evaluate existing content, paste the exact lines verbatim into the brief and ask for a verdict on each — stands, needs narrowing with replacement wording, or unsupported. Naming the file instead gets you a review of the file."
>
> *Grounded in: four evidence lines rewritten from per-line verdicts returned against quoted text.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Briefs in this session quoted the specific evidence lines under scrutiny and asked for one of three verdicts on each, with replacement wording required for any narrowing. Readers returned line-by-line judgements that were directly applicable: one line's claim was narrowed from universal to eleven of thirteen, another had a qualifier removed because it no longer applied, and a third was rewritten to carry the statistical weakness of its underlying experiment. A brief that says "review this page" returns prose about the page, which then has to be translated into edits by the orchestrator — who is the party least able to check it. The marginal cost is pasting a few lines; the return is edits that can be applied verbatim.

### Suggestion 6: Relaunch subagents after an interrupt; they do not resume — `AGENTS-MD-1b42e37ea1`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-1b42e37ea1-relaunch-subagents-after-an-interrupt-they-do-not-resume.md](./2026-09-13-50/AGENTS-MD-1b42e37ea1-relaunch-subagents-after-an-interrupt-they-do-not-resume.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Relaunch subagents after an interrupt; they do not resume.** "Interrupting a turn stops every background subagent it started, and a stopped subagent cannot be resumed by messaging it. After any interrupt, list the running agents, assume the ones you started are gone, and relaunch with the corrected brief rather than trying to redirect them."
>
> *Grounded in: a mid-flight scope change that found all four readers already stopped by the interrupt that delivered it.*

**Justification** (verbatim from the per-rule file's `# justification` section):

When the owner interrupted a turn to exclude one file from a source, the natural response was to message the affected reader with the scope change. The message failed: the agent had been stopped by the interrupt and would not be resumed. Listing the running agents showed all four were gone. The recovery — relaunching three readers with the exclusion written into the brief — was strictly better anyway, because the exclusion then appeared in the instructions rather than as a correction the reader had to apply to work already done. The cost of the rule is one listing call after an interrupt. The cost of not having it is a silent assumption that redirected agents are still working, and a wait for results that will never arrive.

### Suggestion 7: Never invent a rating for material you could not fetch — `AGENTS-MD-6e9abbf635`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-6e9abbf635-never-invent-a-rating-for-material-you-could-not-fetch.md](./2026-09-13-50/AGENTS-MD-6e9abbf635-never-invent-a-rating-for-material-you-could-not-fetch.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Never invent a rating for material you could not fetch.** "If a source cannot be retrieved, do not give it a relevance rating, a summary, or a triage row inferred from its title or its citing document. Record the attempt, the exact URL, the failure, and the date where the next session will see it, and say plainly that it is unfetched."
>
> *Grounded in: a catalogue cited by an ingested paper whose published path returned 404 and whose repository returned 403.*

**Justification** (verbatim from the per-rule file's `# justification` section):

A paper ingested in this session cited a companion catalogue by URL. The site was live; the cited path returned 404 and the repository returned 403. The corpus's triage table requires a relevance rating on every row, and a rating could have been inferred plausibly from the citing paper — which is exactly how a fabricated assessment enters a corpus whose entire value rests on traceability. The item went into the capture file instead, with the URL, both status codes, and the date. A future session can retry or ask the authors. The marginal cost is one line in a different file; the cost of the alternative is a corpus row asserting a judgement nobody made.

### Suggestion 8: Seed a shared vocabulary before parallel naming — `AGENTS-MD-d25122c734`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-d25122c734-seed-a-shared-vocabulary-before-parallel-naming.md](./2026-09-13-50/AGENTS-MD-d25122c734-seed-a-shared-vocabulary-before-parallel-naming.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Seed a shared vocabulary before parallel naming.** "Before dispatching parallel agents that may propose names, give every brief the existing vocabulary and require reuse, with new names flagged explicitly. Reconcile collisions before anything is written."
>
> *Grounded in: three readers proposing the same new idea as `hand-fixed-validation`, `fix-source-not-environment` and `verify-from-clean-state`.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Three readers working on three slices of one source independently identified the same missing concept and proposed three different names for it. The briefs had carried the existing vocabulary and required reuse, which is why the collision was visible and cheap: the three proposals arrived side by side and merged into one page before anything was committed. Without the shared vocabulary, the same three findings would have mapped onto three different existing pages as well, scattering the evidence. This rule was proposed in an earlier retrospective and never assembled into force; the collision recurred in this session, which is the second data point and the argument for adopting it rather than proposing it again.

### Suggestion 9: A retrospective rule that was never assembled binds nothing — `AGENTS-MD-7e0e67be67`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-7e0e67be67-a-retrospective-rule-that-was-never-assembled-binds-nothing.md](./2026-09-13-50/AGENTS-MD-7e0e67be67-a-retrospective-rule-that-was-never-assembled-binds-nothing.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **A retrospective rule that was never assembled binds nothing.** "Do not treat a rule proposed in a past retrospective as being in effect. Before relying on one, check whether it reached the agents file or a hook; if it did not, either assemble it or treat the behaviour as ungoverned."
>
> *Grounded in: a prior retrospective's rule about checking generated files for empty fields, which was never assembled, while the artifact it described stayed broken.*

**Justification** (verbatim from the per-rule file's `# justification` section):

An earlier retrospective in this repository proposed a rule requiring generated files to be grepped for empty extracted fields, grounded in the exact artifact this session had to repair. The rule was written, committed, and never assembled into the agents file — so it governed nothing, and the truncated artifact it described survived untouched until a human noticed it months later. The corpus this session maintains now documents precisely this failure mode as its own pattern: prose that is not in force does not bind. The marginal cost of the rule is one check before citing a past retrospective as authority. The cost of skipping it is the belief that a problem is handled because somebody once wrote that it should be.

### Suggestion 10: Name the successor when you deprecate — `AGENTS-MD-c7ac93e002`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-c7ac93e002-name-the-successor-when-you-deprecate.md](./2026-09-13-50/AGENTS-MD-c7ac93e002-name-the-successor-when-you-deprecate.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Name the successor when you deprecate.** "When retiring a rule, pattern, or check, state in the deprecation note where each surviving part of its function went. If no successor exists, say that explicitly rather than leaving the gap unremarked."
>
> *Grounded in: two deprecations whose surviving functions were distributed across four other pages.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Two pages were deprecated in this session on the owner's judgement. A reader of the supporting source pointed out that the defects which had actually surfaced were not the kind the deprecated practice would have caught — and warned that deprecating without naming a replacement would remove a function from the corpus while leaving nothing in its place. The deprecation notes were written to name, part by part, which pages absorbed which function. Writing them forced the question "what catches this now?" at the only moment the answer was still fresh. The marginal cost is two sentences per deprecation; the cost of omitting them is a corpus that quietly loses capabilities and cannot say when.

### Suggestion 11: Refresh the prompt of any routine you created — `AGENTS-MD-51136dba9d`

- **Per-rule file**: [./2026-09-13-50/AGENTS-MD-51136dba9d-refresh-the-prompt-of-any-routine-you-created.md](./2026-09-13-50/AGENTS-MD-51136dba9d-refresh-the-prompt-of-any-routine-you-created.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Refresh the prompt of any routine you created.** "A scheduled routine only ever sees its own stored prompt, never the conversation. Whenever the situation it describes changes, update that prompt in place — never by deleting and recreating it — and delete the routine outright once its subject is finished."
>
> *Grounded in: a check-in routine that kept re-raising a question the user had already answered, because its prompt still contained it.*

**Justification** (verbatim from the per-rule file's `# justification` section):

A check-in routine created in this session carried the text of an open question and a recommendation. The user answered it in chat. The routine's stored prompt did not change, so the next firing re-raised the settled question, and would have gone on doing so indefinitely. The same routine also carried standing context worth keeping — that the repository has no CI, so check runs are always empty — which is exactly why deleting and recreating it is the wrong repair: that discards the run history along with the stale text. Updating in place costs one call. Leaving it costs a recurring job that argues with decisions the user has already made.
