## Part 1 — what happened

### Phase 1 — Issue intake and parallel blind profiling

Goal: answer issue #22 ("what do specs that an agent can build in one shot
have in common?") using the three StrongDM Attractor specs and OpenAI's
Symphony SPEC.md as the evidence base. The four specs total ~7,900 lines /
~360 KB — too much to analyze in one context alongside synthesis work.

Approach that worked: download all four via `curl` to raw.githubusercontent.com
(the GitHub MCP tools are scoped to this repo, but plain HTTPS fetch of
user-supplied public URLs goes through the proxy fine), then dispatch **four
parallel Explore subagents, each given the identical 14-dimension rubric and
no sight of the others' work**. The blindness was deliberate: convergence
across independent profiles is signal; profiles that could see each other
would anchor. All four returned uniform, line-number-anchored profiles that
were publishable nearly verbatim.

The single highest-value rubric dimension turned out to be the one that asked
for *weaknesses*: "find the 2–3 places where the spec is LEAST precise." The
resulting ambiguity audits (undefined pseudocode helpers, dangling config
references, internal contradictions — in *gold* specs) became the checklist's
"lint pass" section and, later, the regression corpus requirement in task-03.
Asking "where does the best-in-class example still fail?" produced more
reusable material than any amount of praise-shaped analysis.

### Phase 2 — Synthesis, checklist, PR #23

Intersecting the four profiles gave 12 shared attributes (binary DoD
checklists in all four being the most striking), plus the equally useful
*differences* — RFC-2119 keywords and markdown tables vary wildly among
successful specs, so they are not necessary conditions. Deliverable:
`spec-completeness/README.md` (method, findings, ~45-item checklist, ranked
causal hypotheses with research citations, ablation protocol) plus the four
profiles as evidence files.

One self-caught defect: the synthesis claimed "all four specify retry backoff
as an equation." A full top-to-bottom reread before committing caught that
coding-agent-loop *delegates* backoff to its companion spec rather than
stating a formula. Fixed pre-commit. This is exactly the cross-section-drift
failure mode the reread pass exists for; it fired on the first real use.

PR #23 opened and merged by the owner the same day.

### Phase 3 — Conceptual expansion (chat-only, correctly)

The owner asked three follow-on questions: relation to RUP-style artifact
processes, an iterative idea→spec path, and hardening the checklist beyond
existence checks. These were assessment questions, answered in chat without
touching the repo — the RUP mapping ("gold specs are RUP's artifact *content*
with the process ceremony deleted, because the consumer changed from many
human minds to one agent context"), a staged process sketch, and the three
probe families (closure cross-products, independent-reader divergence,
mutation testing of the gate).

### Phase 4 — Scope correction mid-flight, pivot to task files, PR #24

The owner then asked to expand all three into concrete deliverables,
including "task definitions… so the work can be split into multiple
sessions." I read the decomposition unit wrong: I planned to author the
artifact model and process docs inline *now* and write ~10 task files for the
hardening checks, and had already written a complete `artifact-model.md`
draft when the correction arrived: **one task file per idea, three total —
each idea deserves its own dedicated session.**

Recovery pattern (worth keeping): *distill, don't discard*. The finished
draft was deleted as a deliverable, but its design content — layers, artifact
IDs, Freedom Register, traceability rules, validation-by-decomposition — was
compressed into task-01's "design direction" section, explicitly labeled a
hypothesis the future session may restructure with reasons. Nothing of value
was lost, and the future session isn't handed pre-anchored "finished" prose.

The three task files were then written to a common shape that dogfoods the
session's own findings: context-to-load, objective, design direction (marked
as hypothesis), validation requirements grounded in the profiles' known
defects, deliverable paths, a per-task acceptance checklist (a DoD for the
task itself), out-of-scope, and provisional-vocabulary fallbacks so dependent
tasks can start before their dependency merges. PR #24 opened, then merged on
the owner's explicit instruction.

### Phase 5 — Operational housekeeping and environment friction

Three tool-level stumbles, all recovered, all worth recording (see
agents-file suggestions): the `send_later` self check-in could not be armed —
first call used a wrong tool name, retry hit "MCP tool call requires
approval," which a non-interactive session cannot grant; a
`--force-with-lease` push failed with "stale info" because GitHub had deleted
the remote branch on merge, fixed by `git fetch --prune` then plain push; and
the GitHub MCP server disconnected/reconnected mid-session, requiring
ToolSearch reloads. PR-merge webhooks auto-unsubscribed the session both
times, which made the un-armable check-in moot.

## Part 4 — proposed ADRs

Architectural decisions made in this session that may be worth recording.
Titles only — author any of these via the `adr` skill if they earn it.

- **Spec-completeness work lives under `spec-completeness/` with `tasks/` as the session work queue** — the directory convention was established across PRs #23/#24 and future sessions will assume it.
- **Cross-session work is coordinated via self-contained task files, one per session-sized unit** — the owner explicitly chose this granularity ("all three have enough complexity that they deserve dedicated sessions"); it is now the repo's multi-session workflow contract.
- **One-shot spec authoring adopts strict WHAT/HOW layering with an explicit Freedom Register** — the owner's central requirement in the artifact-model discussion; binds task-01 and everything downstream.
- **Completeness checks are tiered: deterministic automation > constrained-context ephemeral LLM > human review, with an escalation-ladder rule** — the owner's stated preference ordering; binds task-03 and any future check tooling.
