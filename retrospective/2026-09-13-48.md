## Part 1 — what happened

The session had one nominal task — transcribe a PDF of handwritten notes into `13-scoped-sandbox.md` — and grew, by the author's direction at each step, into two transcription skills, a second document, a long design conversation, and a new kind of document (a by-topic capture of that conversation) with a skill to reproduce it. No subagents were used; everything ran in the main context.

### Phase 1 — transcribing the scoped-sandbox notes (#44 opened)

`Read` could not render the PDF (`pdftoppm` missing), `apt-get install poppler-utils` returned 404, and `pip install pymupdf` worked. The scan was one 514×2306-point page; it was split into six page-width-proportioned chunks at 300 dpi and read chunk by chunk. Three words were zoomed at 500–900 dpi (`MCP` vs `MLP`, `AI files`, `scope/change`); one — the last word of a margin annotation — would not resolve and was marked inline rather than guessed. The document was saved with a `## Raw transcription` section and pushed as PR #44.

### Phase 2 — the transcription skill, applied to itself, then corrected (#45, #46)

The author asked for a lightweight skill encoding what had just been done — chunk-by-chunk display next to the source, ask how to save if unspecified (with display-only offered), preserve the raw transcription, ask whether to discuss or organize — and for it to be committed, PR'd, and merged separately before continuing. `handwritten-notes-transcription` (212 lines, plus `render_pages.py`) merged as #45. Applying it back to the transcription produced the verification display and the ambiguity zoom; the author resolved the word by saying the margin note belonged to the *next* line and expanding it to a full sentence, and asked that three lines become three bullets.

The skill's strict-verbatim rule then misfired: folding the author's expansion in with a bracketed provenance note drew "Take out the bracketed note. My intention was to rearrange and add sentence when transcribing." The rule was wrong for how the author works. The revision (#46) replaced it with one governing section — *author intent in, agent invention out; enhancement fenced until capture is done* — and, at the author's request, cut the skill to 166 lines. An untested numeric claim about chunk heights was cut in the same pass.

### Phase 3 — the secrets notes, via the skill, isolated (#47)

A second PDF (`14-scoped-secrets.md`, "stop at transcription") went through the merged skill: two chunks, three zooms, two author corrections (`w/secrets` joins the next line; an L-shaped mark is a dash bullet). It had been committed onto the #44 branch; the author asked for an isolated PR, so it was carved onto a fresh branch from `main`, merged as #47, and `main` merged back so #44's diff returned to one file.

### Phase 4 — the design conversation (no commits)

The author stated the motivation — encapsulation as an attention aid for a human and an agent who both lose the thread on context switches — and asked for reaction with "make no changes yet." Two long exchanges followed: the agent's read (attention-scoping over enforcement, four-field MVP, recreatability as the key tag) and the author's response (behavioral lens; ADHD and autism named; no stubs; agent judges task size and adapts; snapshot as file list plus commit hash plus bead; Later is a file; credentials as one convenience key). The agent's task-size tripwire was withdrawn; its "stubs as empty fields" middle ground was overtaken by the author going further.

### Phase 5 — Appendix A, the by-topic capture (#44 continued, merged)

The author asked to capture "all the ideas from my original notes, these prompts, and your reactions" into an appendix of `13-scoped-sandbox.md`, doing for the session what the skill had done for the page. The agent proposed conversation order and verbatim quotation of the author; the author redirected: theme not time, compress both voices, include rejected suggestions, inject the agent's read of intent as interpretation, no conclusions, include the meta-round. Thirteen sections were written. A re-read pass caught three overstatements before commit; the author caught a fourth class — seven statements marked *explicit decision* were opinions at a point in time — and the markers became *stated position*. The author merged #44.

### Phase 6 — the preserve-context skill (#48)

"What you produced is exactly what I wanted." The author asked for a skill that reproduces it on explicit trigger, for the current session or a past transcript. `preserve-context` (190 lines plus a template) was written to the short-skill shape, PR'd, and merged on the author's word when the GitHub UI misbehaved.

### Suggestion 1: Render PDFs with PyMuPDF; apt is unreliable in this sandbox — `AGENTS-MD-bc2750fb93`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-bc2750fb93-render-pdfs-with-pymupdf-apt-is-unreliable-in-this-sandbox.md](./2026-09-13-48/AGENTS-MD-bc2750fb93-render-pdfs-with-pymupdf-apt-is-unreliable-in-this-sandbox.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Render PDFs with PyMuPDF; apt is unreliable in this sandbox.** When `Read` on a PDF fails because `pdftoppm` is missing, do not reach for `apt-get install poppler-utils` — the package mirror returns 404 here. Run `pip install pymupdf` and render pages with it. The `handwritten-notes-transcription` skill's `scripts/render_pages.py` already wraps this, including splitting very tall single-page scans and re-rendering one rectangle at high DPI.
>
> *Grounded in: first attempt to read the scoped-sandbox notes PDF.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The first PDF of the session could not be read by the `Read` tool (no `pdftoppm`), and the reflex fix — `apt-get install poppler-utils` — failed with a 404 from the Ubuntu mirror. `pip install pymupdf` succeeded in seconds and rendered every page at any DPI needed for the rest of the session, including 2000 dpi zooms on single words. Without this rule the next session repeats the two failed attempts before finding the one that works. Marginal cost of the rule: one pip command, already scripted.

### Suggestion 2: Start follow-up work from a fresh branch off origin/main after a merge — `AGENTS-MD-64fed5f8d3`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-64fed5f8d3-start-follow-up-work-from-a-fresh-branch-off-originmain-after-a-merge.md](./2026-09-13-48/AGENTS-MD-64fed5f8d3-start-follow-up-work-from-a-fresh-branch-off-originmain-after-a-merge.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Start follow-up work from a fresh branch off origin/main after a merge.** When a PR merges, do not reset or force-push the merged branch to reuse it. Run `git checkout -b <new-branch> origin/main` and work there. `git checkout -B`, `git reset --hard`, and `git push --force-with-lease` are classified as destructive in this environment and are denied, so the reset-in-place pattern stalls even when the branch holds only merged history.
>
> *Grounded in: post-#44 branch reset denied twice.*

**Justification** (verbatim from the per-rule file's `# justification` section):

After PR #44 merged, two attempts to move the designated branch onto the new `main` were denied by the auto-mode classifier — first the combined `checkout -B` + `force-with-lease`, then `checkout -B` alone — and a plain fetch was then declined by the author. The session lost three tool calls and had to explain itself. The alternative, a fresh branch from `origin/main`, was accepted immediately for both the `preserve-context` skill and this retrospective and costs one command. Nothing about the old branch needs preserving after a squash merge; the content is on `main`.

### Suggestion 3: One artifact per pull request for idea documents and skills — `AGENTS-MD-3fade0ecfb`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-3fade0ecfb-one-artifact-per-pull-request-for-idea-documents-and-skills.md](./2026-09-13-48/AGENTS-MD-3fade0ecfb-one-artifact-per-pull-request-for-idea-documents-and-skills.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **One artifact per pull request for idea documents and skills.** Each idea document (`NN-name.md`) and each skill change goes in its own PR, branched from `origin/main`. If a file lands on a shared working branch by accident, carve it out: `git checkout -b <new> origin/main && git checkout <shared-branch> -- <file>`, commit, PR, merge; then merge `origin/main` back into the shared branch so its diff returns to one artifact.
>
> *Grounded in: PR #47 carved out of the #44 branch on request.*

**Justification** (verbatim from the per-rule file's `# justification` section):

`14-scoped-secrets.md` was first committed onto the scoped-sandbox branch alongside `13-scoped-sandbox.md`. The author asked for "an isolated pr for this transcription." The carve-out took two commands, PR #47 merged with one call, and merging `main` back left #44's diff at exactly one file again. Four of the session's five PRs were isolated this way and every one merged cleanly — including when the author said the GitHub UI was "being strange" and just wanted one thing merged. A shared branch carrying two documents would have forced merging both or neither. Cost of the rule: one extra branch per artifact.

### Suggestion 4: Skills in this repo are short and lead with the governing rule — `AGENTS-MD-426c942214`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-426c942214-skills-in-this-repo-are-short-and-lead-with-the-governing-rule.md](./2026-09-13-48/AGENTS-MD-426c942214-skills-in-this-repo-are-short-and-lead-with-the-governing-rule.md)

Cut worked examples that only restate a rule already given. Aim under ~200 lines. The author's standard, verbatim: "Skills should be helpful and unambiguous and short."

### Suggestion 5: No untested numeric claims in a skill — `AGENTS-MD-f3ad91ddd4`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-f3ad91ddd4-no-untested-numeric-claims-in-a-skill.md](./2026-09-13-48/AGENTS-MD-f3ad91ddd4-no-untested-numeric-claims-in-a-skill.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **No untested numeric claims in a skill.** Do not write a threshold, size, DPI, or limit into a skill that you have not measured in the session that produced it. If the number matters, test it once and say what was tested; if you can't, state the principle without the number.
>
> *Grounded in: "1500–1800 points read reliably; a 2300-point page does not," written untested.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The first `handwritten-notes-transcription` skill asserted that chunks of 1500–1800 points read reliably and a full 2300-point page does not. Neither had been tried — the page had simply been split into 384-point chunks and read. When the skill was applied to verify its own output, a 1173-point chunk read fine at a glance, and the full-page case was never tested at all. The numbers were cut in the revision. A wrong number in a skill is trusted by every future run; testing it costs one render.

### Suggestion 6: Idea documents record positions, not decisions — `AGENTS-MD-6d183180da`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-6d183180da-idea-documents-record-positions-not-decisions.md](./2026-09-13-48/AGENTS-MD-6d183180da-idea-documents-record-positions-not-decisions.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Idea documents record positions, not decisions.** In `NN-name.md` idea documents and session captures, never write "decided", "agreed", or "explicit decision" about the idea itself unless the author called it a decision. Mark firm statements *stated position*. The only decisions a capture records by default are process decisions — how the document itself was made.
>
> *Grounded in: Appendix A of 13-scoped-sandbox.md, seven markers replaced.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The first draft of Appendix A marked seven of the author's statements as *explicit decision*. The author corrected it: the only decisions made were how the notes were transcribed and how the capture was made; everything else was "a statement of my opinion at a specific point in time. I don't want decisions solid until later." A decision label in a document meant to stay open forecloses the later thinking the document exists to support. Fixing it took a commit and a PR-body edit; getting it right costs a word choice.

### Suggestion 7: Re-read for attribution drift when writing on the author's behalf — `AGENTS-MD-8b6678a90c`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-8b6678a90c-re-read-for-attribution-drift-when-writing-on-the-authors-behalf.md](./2026-09-13-48/AGENTS-MD-8b6678a90c-re-read-for-attribution-drift-when-writing-on-the-authors-behalf.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Re-read for attribution drift when writing on the author's behalf.** After drafting anything that speaks for the author — a transcription, a session capture, a PR description of their idea — do one full pass hunting for: your inference presented as their words; a hedge they used ("probably", "for now", "with a little more nuance") that you dropped; "decided" where they stated a position; an idea that quietly vanished. Fix each before showing it.
>
> *Grounded in: the Appendix A re-read caught three; the author caught a fourth.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The re-read of Appendix A before its first commit caught three places where the agent had put words in the author's mouth: their wife's comment recorded as "adopted as the brief" when they had said "with a little more nuance"; an inference ("git-tracked-or-not subsumes the flag") stated as theirs; and a table mixing agreed and open items without saying so. The author then caught a fourth class — decisions versus positions — that the pass had not been looking for. The cost of not re-reading is that the author has to catch it, and until they do the document misrepresents them. The cost is one read with a short checklist.

### Suggestion 8: Create the PR and offer to merge; merge only on the word — `AGENTS-MD-b1ef5fc0c2`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-b1ef5fc0c2-create-the-pr-and-offer-to-merge-merge-only-on-the-word.md](./2026-09-13-48/AGENTS-MD-b1ef5fc0c2-create-the-pr-and-offer-to-merge-merge-only-on-the-word.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Create the PR and offer to merge; merge only on the word.** Open the PR, say it is ready, and stop. Merge only when the author says so, with squash, and confirm the merged SHA. When they ask because the GitHub interface is misbehaving, that is the instruction — merge, don't investigate the interface.
>
> *Grounded in: five PRs, each merged only on explicit instruction.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Every PR in the session (#44–#48) was merged only after the author said "merge" — once with "merge just the skill edits," once with "the GitHub interface is being strange." Twice the agent created a PR and explicitly did not merge because it had only been asked to create; the author then asked, and the merge was one call. The author's stated preference is that the agent do exactly what was asked and confirm before doing more. Cost of the rule: one round-trip per merge. Cost of breaking it: a merge the author did not want on `main`.

### Suggestion 9: Refresh the PR description when the PR's content changes — `AGENTS-MD-92fed23ffb`

- **Per-rule file**: [./2026-09-13-48/AGENTS-MD-92fed23ffb-refresh-the-pr-description-when-the-prs-content-changes.md](./2026-09-13-48/AGENTS-MD-92fed23ffb-refresh-the-pr-description-when-the-prs-content-changes.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Refresh the PR description when the PR's content changes.** When a later push materially changes what a PR contains — a new section, a second document, a resolved ambiguity — update the PR title and body in the same turn as the push. A stale body misleads the reviewer now and the future reader mining the PR later.
>
> *Grounded in: #44's body still described one file and an open ambiguity after the appendix landed.*

**Justification** (verbatim from the per-rule file's `# justification` section):

PR #44 opened as "one transcription, one uncertain word." By merge time it carried a resolved transcription, a 390-line appendix, and a correction about decisions — and its body had been refreshed twice, each time after the agent noticed the drift rather than as part of the push. The idea-pipeline treats merged PRs as a record (the retrospective skill mines them by number), so a stale body is a stale record. Updating the body is one tool call in the turn that already pushed.
