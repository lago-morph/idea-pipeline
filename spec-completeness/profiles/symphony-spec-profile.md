# Document Profile: Symphony Service Specification (`SPEC.md`)

**Quantitative overview:** 2,185 lines (openai/symphony `SPEC.md`). Headings: 1×H1, 20×H2, 83×H3, 16×H4 (120 total). 11 fenced code blocks (5 `json`, 6 `text` pseudocode). **Zero Markdown tables** — the doc is entirely prose + nested bullet lists despite calling several sections "matrix"/"cheat sheet"/"table." ~829 dash-bullet lines and ~72 numbered-list items. Normative keyword counts: MUST 26 (+ 6 MUST NOT), SHALL 0, REQUIRED 23, SHOULD 50 (+ 4 SHOULD NOT), RECOMMENDED 13, MAY 23, OPTIONAL 34.

## 1. Purpose & Scope
Specifies **Symphony**, a long-running daemon that polls an issue tracker (Linear), creates per-issue filesystem workspaces, and runs a Codex coding-agent session per issue with bounded concurrency, retries, and reconciliation. Goals AND non-goals are **both explicit and adjacent** (§2.1 lines 46-56; §2.2 lines 58-67), and an unusual "Important boundary" note (lines 36-42) pre-empts scope confusion by clarifying Symphony is a *reader/runner*, not a ticket-writer.
> "Non-Goals: Rich web UI or multi-tenant control plane... General-purpose workflow engine or distributed job scheduler." (lines 60-62)

## 2. Document Structure
18 numbered top-level sections + a Normative-Language preamble + Appendix A. Ordering is deliberate and textbook: **framing** (§1-2 problem/goals) → **architecture** (§3 components/layers) → **data model** (§4) → **contracts/config** (§5-6) → **behavior** (§7-10 state machine, scheduling, workspace, agent protocol) → **integration** (§11-13 tracker, prompt, observability) → **failure** (§14-15) → **reference algorithms** (§16) → **conformance** (§17 test matrix, §18 checklist). Section inventory with line numbers: Normative Language (7), 1 Problem Statement (16), 2 Goals/Non-Goals (44), 3 System Overview (69), 4 Core Domain Model (146), 5 Workflow Spec (289), 6 Configuration (502), 7 Orchestration State Machine (604), 8 Polling/Scheduling/Reconciliation (702), 9 Workspace Mgmt/Safety (818), 10 Agent Runner Protocol (914), 11 Tracker Integration (1141), 12 Prompt Construction (1225), 13 Logging/Observability (1258), 14 Failure Model (1533), 15 Security (1618), 16 Reference Algorithms (1692), 17 Test/Validation Matrix (1931), 18 Implementation Checklist (2076), Appendix A SSH Worker (2125).

## 3. Data Model
Entities are specified **language-neutrally** in §4.1 with per-field bulleted "tables" (name + parenthesized type + inline constraint notes), not native signatures and not fenced tables. Eleven-ish entities are covered (Issue, WorkflowDefinition, ServiceConfig, Workspace, RunAttempt, LiveSession, RetryEntry, OrchestratorRuntimeState). Field types use a portable vocabulary (`string or null`, `list of strings`, `integer`, `timestamp or null`). Fields are exhaustive for the core entities (e.g., LiveSession lists 14 token/timestamp fields, lines 229-245). Enums are **partially** enumerated: orchestration states (5, lines 614-630) and run-attempt phases (11, lines 649-659) are fully listed, but Codex-owned enums (`approval_policy`, `thread_sandbox`, `turn_sandbox_policy`) are **deliberately delegated** to the external Codex schema rather than enumerated (lines 436-442).
> "`Workspace Key` — Derive from `issue.identifier` by replacing any character not in `[A-Za-z0-9._-]` with `_`." (lines 281-282)

## 4. Interfaces / API Surface
Mixed precision by layer. Tracker adapter operations are given **exact names + intent** but loose signatures: `fetch_candidate_issues()`, `fetch_issues_by_states(state_names)`, `fetch_issue_states_by_ids(issue_ids)` (lines 1147-1154). The HTTP extension defines **exact routes, methods, status codes, and full JSON response bodies** (§13.7.2: `GET /api/v1/state`, `GET /api/v1/<issue_identifier>`, `POST /api/v1/refresh`; 404/405/202 semantics; lines 1401-1529). The Codex app-server wire protocol is **intentionally NOT specified** — the spec repeatedly defers to "the targeted Codex app-server version" as source of truth (lines 918-928). The `linear_graphql` tool gets a precise input schema and result-semantics contract (lines 1064-1095).

## 5. Behavioral Semantics
This is the spec's strongest dimension. Behavior is given **deterministically** via: a named state machine (§7), an ordered 6-step tick sequence (§8.1 lines 711-718), explicit candidate-eligibility conjunction (§8.2 lines 725-736), exact concurrency/backoff formulas, and — most precisely — **6 blocks of language-agnostic pseudocode** in §16 covering startup, tick, reconcile, dispatch, worker-attempt turn loop, and worker-exit/retry (lines 1696-1929). Ordering guarantees ("Reconciliation runs before dispatch on every tick," line 698) and idempotency rules (§7.4) are stated. The single most precise example is the backoff formula:
> "Failure-driven retries use `delay = min(10000 * 2^(attempt - 1), agent.max_retry_backoff_ms)`." (line 767)

Concurrency is described as single-authority serialization (line 606, 696) but the *mechanism* (actor/mutex/event-loop) is left to the implementer.

## 6. Defaults & Configuration
Nearly every knob has an **explicit default**, and §6.4 is a redundant "cheat sheet" (lines 578-602) restating all core fields + defaults specifically "so a coding agent can implement the config layer quickly" (line 574). Examples: `polling.interval_ms: 30000`, `hooks.timeout_ms: 60000`, `agent.max_concurrent_agents: 10`, `agent.max_turns: 20`, `agent.max_retry_backoff_ms: 300000`, `codex.turn_timeout_ms: 3600000`, `codex.read_timeout_ms: 5000`, `codex.stall_timeout_ms: 300000`, `tracker.active_states: ["Todo","In Progress"]`. The **only defaults deliberately left open** are the three Codex policy enums, marked `default: implementation-defined` (lines 449-453) — a documented, not accidental, gap.

## 7. Error Handling & Edge Cases
Systematic and pervasive. Named error taxonomies appear in multiple sections: workflow errors (§5.5, 5 classes), tracker errors (§11.4, 8 categories), agent error-mapping (§10.6, 9 categories), and a full failure-class catalog (§14.1, 5 classes). Each error specifies its **blast radius** (e.g., "Workflow file read/YAML errors block new dispatches until fixed. Template errors fail only the affected run attempt," lines 499-500). Hook failure semantics are enumerated per-hook (fatal vs. logged-and-ignored, lines 887-892). Edge/boundary cases are called out explicitly: empty `fetch_issues_by_states([])` short-circuits without an API call (line 1987), `stall_timeout_ms <= 0` disables stall detection (line 460), blank configured label matches no issue (line 365), non-directory path already at workspace location (line 1973), missing end-cursor pagination integrity error (line 1205). Timeouts and retries are first-class throughout.

## 8. Examples
Worked examples are **moderate and concentrated in I/O shapes, not narrative walkthroughs**. 11 fenced blocks: 5 JSON payloads (the `linear_graphql` input schema plus four full HTTP-API request/response bodies with realistic values like `"MT-649"`, `turn_count: 7`, lines 1406-1521) and 6 pseudocode algorithm blocks (§16). There is **no single end-to-end narrative** ("issue X arrives → dispatched → agent runs → handoff") tying it together; the reader assembles the flow from §16's separate functions. Inline literal examples are sprinkled in prose (e.g., `ABC-123` identifier, `<thread_id>-<turn_id>` session-id format).

## 9. Acceptance Criteria / Conformance
Exceptionally strong — this is a defining feature. **Two dedicated sections**: §17 "Test and Validation Matrix" (~90 testable bullet assertions across 8 subsections) and §18 "Implementation Checklist (Definition of Done)" (~26 checklist items). Both are organized under **three named validation profiles** — `Core Conformance`, `Extension Conformance`, `Real Integration Profile` (lines 1938-1945) — with an explicit convention that "Bullets that begin with `If ... is implemented` are `Extension Conformance`" (line 1945). §18 cross-references §17's profiles by number. Assertions are concrete and testable (e.g., "`Todo` issue with non-terminal blockers is not eligible," line 1998).

## 10. Normative Language
Full RFC-2119 adoption, declared up front (lines 7-14). Prescription vs. suggestion is cleanly separated by keyword. Rough counts: **MUST 26 / MUST NOT 6 / REQUIRED 23** (hard requirements) vs. **SHOULD 50 / SHOULD NOT 4 / RECOMMENDED 13** (strong advice) vs. **MAY 23 / OPTIONAL 34** (latitude). Zero SHALL. The heavy tilt toward SHOULD+MAY+OPTIONAL (~110) over MUST-class (~55) reflects the spec's portability posture. It also defines a **custom keyword** beyond RFC-2119:
> "`Implementation-defined` means the behavior is part of the implementation contract, but this specification does not prescribe one universal policy. Implementations MUST document the selected behavior." (lines 12-14)

## 11. Implementation Freedom
Explicitly and repeatedly bounded. The title tagline is "language-agnostic" (line 3); §3.2 prescribes a 6-layer abstraction model "easiest to port" (lines 114-137); §16 algorithms are labeled "Language-Agnostic." Freedom is granted for: language/runtime, log sinks, dashboard tech (HTML vs. SPA), trust/sandbox posture, workspace population/VCS strategy, and timer/concurrency mechanism. Crucially, freedom is **bounded by output contracts**: "A non-Linear implementation MAY change transport details, but the normalized outputs MUST match the domain model in Section 4." (lines 1178-1179). Optionality is structurally fenced via the `OPTIONAL`/extension markers (Status Surface, HTTP server, `linear_graphql`, SSH worker are all opt-in).

## 12. Self-Containedness
**Mostly self-contained for the orchestration core**, but *not* fully self-contained for the agent-protocol boundary. An implementer can build the scheduler, config layer, workspace manager, retry/reconciliation logic, and tracker adapter purely from this doc. However, the Codex app-server integration **explicitly requires an external document**: it cites `https://developers.openai.com/codex/app-server/` (line 951) and instructs running `codex app-server generate-json-schema` to discover message shapes and enum values (lines 438-442). It also assumes background knowledge of Linear's GraphQL schema, RFC 2119, Liquid template semantics (line 468), YAML front matter, and ISO-8601. So: self-contained for behavior, deliberately deferential for wire protocol.

## 13. Ambiguity Audit
The 2-3 least-precise spots (all appear intentional but they widen implementer variance):
1. **The three Codex policy enums** (`approval_policy`, `thread_sandbox`, `turn_sandbox_policy`), whose valid values AND defaults are both "implementation-defined"/deferred (lines 436-453). The entire approval/sandbox posture — arguably the biggest safety lever — is unresolved by design.
2. **Assignee routing** in candidate eligibility: "It is routed to this worker by the configured assignee..." (lines 729-730) — "configured assignee" is never defined as a config field anywhere (it is absent from the §5.3 front-matter schema and §6.4 cheat sheet), a genuine dangling reference.
3. **"single-authority" concurrency** (§7.4, line 696) and "in-memory runtime state" — the required *guarantee* is clear but the *mechanism* is unspecified, and terms like "Continuous background ticking of runtime totals is not REQUIRED" (line 1342) leave snapshot-timing semantics loose. Also minor: token-extraction is described as "leniently from common field names" (line 1327), inviting divergence.

## 14. Distinctive Techniques
Several patterns a checklist-writer should capture:
- **Named validation profiles as a cross-cutting tagging system** (§17/§18) — the same three-tier profile taxonomy is applied to both the test matrix and the DoD checklist, with a lexical convention ("If ... is implemented" → Extension) for auto-classifying bullets.
- **Deliberate redundancy as a feature** — §6.4 restates all config defaults "intentionally... so a coding agent can implement the config layer quickly" (line 574).
- **Explicit source-of-truth precedence / conflict-resolution clause** — "If this specification appears to conflict with the targeted Codex app-server protocol, the Codex protocol controls" (lines 925-926).
- **Custom normative term** (`Implementation-defined`) extending RFC-2119 with a mandatory-documentation obligation.
- **A layered portability model** (§3.2) offered explicitly to ease re-implementation in other languages.
- **Invariants section** — §9.5 "Safety Invariants" numbers three hard filesystem invariants (cwd==workspace, path-under-root, sanitized key) and flags them "the most important portability constraint" (lines 894-913).
- **Reference-algorithm appendix in pseudocode** (§16) that mirrors, function-by-function, the prose behavior — effectively an executable-shaped spec of the control flow.
- **Explicit TODO/future-work markers** inside the checklist (lines 2111-2116) that fence off deferred scope (persistence, tracker writes, pluggable adapters).
- **Prose "boundary notes"** repeatedly re-asserting the reader/runner-not-writer scope to prevent a whole class of misimplementation.
